# Data Plan

No external data sources: the artifact is populated by user input and its own actions. If that changes, finalize the plan again with a `data_plan` object carrying the `markdown` body.

## Vault data design (as built)

- Multi-vault per pattern (added 2026-10-31 at the user's request "패턴마다 금고 만들기로 확장해줘"): `vault_meta` now holds one row per vault, each with its own name, salt, pattern hash, grid size, and recovery envelope. A drawn pattern opens exactly the vault whose salted hash it matches — the server tries the pattern against every vault's salt (each vault has its own salt, so there is no pattern→vault index to leak). A pattern matching no vault is not just an error: the locked screen offers to create a new vault with that pattern (one confirming redraw plus an optional name), and the same creation flow is reachable from the in-vault "금고" tab. `setupPattern` refuses a pattern that already opens a vault (`pattern_taken`), and `upgradePattern` refuses a new pattern that opens a different vault. `vault_items.vault_id` and `vault_backups.vault_id` (migration `0005_multi_vaults_per_pattern.sql`, existing rows default to vault 1, the pre-existing vault) scope every item and backup block to its vault; each vault has an independent backup chain whose head is that vault's newest block. Every content action resolves the pattern to its vault first and only touches that vault's rows, so one vault's pattern reveals nothing about other vaults — the locked screen shows only a vault count, never names. Inside a vault, the pattern-gated `listVaults` powers the "금고" tab (list, rename via `renameVault`, delete via `deleteVault` — which removes that vault's meta row, item/backup rows, and their blobs only). Switching vaults is locking and drawing the other pattern; there is no master key. Recovery follows the vault: `getRecoveryEnvelope` returns every vault's ciphertext envelope (still not pattern-gated, still useless without a phrase) and the client tries the typed phrase against each, while `getOwnRecovery` serves the opened vault's own status to its recovery tab.
- Pattern lock: the pattern is never stored. `vault_meta` holds a random salt and SHA-256(salt + pattern); every content action re-verifies the drawn pattern server-side before returning anything. Verify-only gating for vault contents — stored file bytes are not encrypted with a pattern-derived key, and the setup screen says so.
- Pattern grid: `vault_meta.grid_size` records the grid the stored pattern was drawn on. Pre-upgrade vaults are 3×3 (migration default), new setups and upgrades are 5×5. The unlock pad renders at the stored size so an existing vault stays openable, and `upgradePattern` re-keys to a new 5×5 pattern after the old one verifies.
- Backup chain ("blockchain-style", Vaultaire-like): each backup is a block in `vault_backups`. The client derives the backup keys from the pattern (PBKDF2-HMAC-SHA-256, 200k rounds, per-backup random salt) and seals every file under its own random nonce. blockHash = SHA-256(prevHash + ":" + createdAt + ":" + comma-joined per-file SHA-256); the first block's prevHash is 64 zero hex digits. `registerBackup` re-derives the block hash server-side, refuses a block whose prevHash is not the current chain head, stores the encrypted package as a blob (`backups/<blockHash>`), and appends the ledger row. The server never sees the backup key or plain file bytes. Restore happens client-side: open the package with the pattern it was sealed with, re-verify the block hash, every file's auth tag, and every file hash, then re-add missing files through the normal `addItem` action.
- Backup cipher v2 (fixed after the user's second "백업이 아직 안됨" report, 2026-10-30): the screenshot showed the exact failure — "암호화 단계에서 멈췄어요: Cannot read properties of undefined (reading 'importKey')". Root cause: v1 did all backup crypto through WebCrypto `crypto.subtle` (importKey for PBKDF2, digest for SHA-256, encrypt for AES-256-GCM), and `crypto.subtle` is undefined outside secure contexts — including the shell/webview this app runs in — so every backup died at key derivation while file reading (the step before) worked. v2 (`client/src/backup.ts`, package `version: 2`, `cipher: "hmac-sha256-ctr-etm"`) removes the WebCrypto dependency entirely: a self-contained pure-TypeScript SHA-256/HMAC/PBKDF2 (verified against Node's crypto on known vectors and full round-trips), master key split into enc/mac subkeys, per-file HMAC-SHA-256 counter-mode keystream with a random 16-byte nonce, and an encrypt-then-MAC HMAC tag appended to each ciphertext and verified before decryption. Verified end-to-end in a simulated subtle-undefined environment: build (~0.8s incl. 200k PBKDF2 rounds), server-formula block hash match, byte-identical restore (text, 150KB binary, empty file), wrong-pattern and tampered-ciphertext rejection. No v1 backup ever succeeded (chain empty), so nothing depends on the old format; v1 packages remain openable where WebCrypto exists, and elsewhere restore says so honestly (`unsupported`) instead of blaming the pattern.
- Mobile: the artifact is a mobile-first web app (phone-width layout, 44px+ touch targets, safe-area padding, standalone/home-screen meta tags in `client/index.html`). It is not a native App Store/Play Store binary.
- Backup byte channel (fixed after the user's "백업이 안됨" report, 2026-10-30): backup creation originally fetched each file's bytes from the browser via the blob URL (`getItemUrl` + `fetch`). The failure evidence: the chain stayed empty and the UI showed only the generic catch-all error, so creation died on an exception path (per-file fetch, client crypto, or the register call) rather than a server refusal, while `addItem` uploads of the same files through the action channel worked. `getItemData` now returns the stored bytes through the action channel (the same channel `addItem` uploads through, proven with the user's real files), read from the blob store by the host-side privileged helper `readBlobBytes` (`server/src/privileged.ts`; objects live at `blobs/objects/<sha256(key)[0..2]>/<sha256(key)>`, legacy fallback `objects/<key>`). The client keeps the blob-URL fetch as a fallback only. The encrypted package is registered as raw JSON text (`packageJson`), dropping the old extra base64 wrap that inflated it by a third. Backup failures now surface the failing step and the underlying error (including HTTP status) in the UI instead of a generic message. Trust level is unchanged: vault bytes are stored unencrypted server-side behind pattern verification, so returning them to the pattern-verified owner via `getItemData` matches `getItemUrl`; the backup package itself is still encrypted client-side and `registerBackup` only ever receives ciphertext.
- Recovery phrase (added 2026-10-30 at the user's request "네, 회복 문구도 추가해줘", Vaultaire-style): a 9-word phrase drawn at random from a 256-word list in `client/src/backup.ts` (one random byte per word, 72 bits of entropy). The client derives keys from the phrase with the same v2 construction as backups (PBKDF2-HMAC-SHA-256, 200k rounds, per-envelope random salt; enc/mac subkeys labelled `vault-recovery-enc-v1`/`vault-recovery-mac-v1`) and seals the pattern itself in an envelope (`format: "vault-recovery"`, version 1). Only the envelope ciphertext is stored, on `vault_meta.recovery_envelope` / `recovery_created_at` (migration `0004_add_recovery_envelope.sql`); the phrase and its keys never leave the device. `setRecoveryEnvelope` and `deleteRecoveryEnvelope` are pattern-gated; `getRecoveryEnvelope` is deliberately not gated — the envelope is ciphertext and reaching it while locked is the point. Recovery flow: locked screen → "회복 문구로 열기" → open the envelope client-side (the HMAC tag judges the phrase; a wrong word is indistinguishable from tampering) → the recovered pattern is re-verified through the normal `unlock` action before anything is shown. Because backups are sealed with the pattern, recovering the pattern also recovers every backup — no second backup key exists. Offered right after first pattern setup (skippable) and managed in the vault's "회복" tab (status, test-a-phrase, replace, delete). `upgradePattern` clears the envelope server-side, since it wraps the old pattern; the upgrade screen and the recovery tab both say a new phrase must be made afterwards. Losing both the pattern and the phrase still loses the vault — the UI states this where the phrase is shown, and the phrase itself is shown only once at creation.
- Mobile download (added 2026-10-30 at the user's request "모바일에서 다운로도 돼도록 만들어줘"): previously every export was an `<a download>` pointing at the server blob URL, which mobile browsers and in-app webviews routinely ignore (cross-origin `download` attribute, sandboxed blob responses), so files did not save on phones. Now all exports — item 꺼내기 and backup files, new and stored — pull the bytes through the action channel (`getItemData`, and the new pattern-gated `getBackupData` for backup packages, read via the same `readBlobBytes` privileged helper) and save a local file client-side: Web Share with a `File` first (the phone share sheet's 파일에 저장 / save-to-Photos path), falling back to a local object-URL anchor download. Backup creation no longer auto-clicks a download at the end of its async flow (no user gesture left by then, so phones dropped it); it leaves the package behind an explicit ‘백업 파일 저장하기’ tap. The app itself remains a home-screen web app, not a store binary; a new ‘설치’ tab (and a ‘모바일 설치·저장 안내’ button on the lock screens) explains that plainly, fires the real `beforeinstallprompt` where the browser offers one, and lists the iPhone Safari / Android Chrome add-to-home-screen steps otherwise.
- In-app source viewer (added 2026-10-30 at the user's request): the "코드" tab in the vault home shows the app's own source code. `getSourceCode` asks the privileged helper `readSourceFiles` to read a fixed list of the artifact's real source files (client, server, migrations, DATA-PLAN.md, space.json) verbatim from the artifact directory, so the viewer always shows the code actually running rather than a bundled copy that could drift. It exposes the application's code only — no vault content, no pattern material — and is therefore not pattern-gated.
